# admin 회원 관리 개편 — 분류에서 관리로 (2026-08-22)

오너 지시: *"우리 어드민 회원관리 너무 정돈이 안되어있는 느낌"*,
*"회원들을 나눠서 볼 수 있는 필터도 좀 있었으면 좋겠어, 유령계정도 있을거고 우리 프로그램에
관심을 갖거나 챌린지에 참여하는 사람들이 있을텐데 사실 이런 사람들이 진성 고객이잖아?"*,
*"뭔가 대기업이나 시스템적으로 어떻게 체계적으로 관리할 수는 없니?"*

목업: `scratchpad/members-mockup.html`(커밋 안 함 — 세션 산출물).

---

## 1. 지금 무엇이 문제인가

측정한 사실만 적는다.

**① 사이드바에 성격이 다른 다섯 덩어리가 순서 없이 쌓여 있다**
검색 → 상태 셀렉트 → '흔적 없는 계정' 3문단 접이 → 일괄 바 → 목록 → 더 보기 → 기수 추가 폼.
300px 폭이다. 기수 만들기는 회원 목록과 다른 일인데 목록 아래 붙어 있고, 일괄 바는 아무것도
안 골랐을 때도 회색 버튼 3개로 자리를 먹는다.

**② 셀렉트 하나에 기준이 다른 7개가 섞여 있다**(`#mFilter`)
전체 · 가입 미완료 · 번호 확인 필요 · 기수 미배정 · 신청 있음 · 흔적 없음 · 보관함.
이 중 '가입 미완료/신청 있음/흔적 없음'은 **회원이 어떤 사람인가**, '번호 확인 필요/기수
미배정'은 **내가 할 일**, '보관함'은 **치워 둔 곳**이다. 고를 때마다 기준이 바뀐다.

**③ 회원 정보 폼의 칸 폭이 제각각이다**(`admin.html:2490`)
`.prow { display:flex; flex-wrap:wrap }` 인데 칸에 폭 지정이 없다. 이름·이메일·연락처·전공·
기수·권한 6칸이 브라우저 기본 폭으로 잡히고 `[정보 저장]` 이 마지막 칸 옆에 그대로 붙어
흐른다. 화면 폭이 바뀌면 접히는 자리가 달라진다.

**④ 분류는 되는데 관리가 안 된다 — 이게 본질이다**
- 이 사람이 **언제 무엇을 했는지**가 한 화면에 없다. 신청·제출물·답변·크레딧이 패널마다 흩어져 있다.
- **내가 아는 것을 적을 칸이 admin 전체에 한 곳도 없다.** 통화 내용, 지망 항공사, 면접 일정.
- 크레딧 잔액을 보려면 다른 탭으로 가야 한다.
- 조건을 조합해 거를 수 없다. "3기 참가자 중 미입금" 은 손으로 훑어야 한다.

**측정해 보니 사실이 아니었던 것(정정)**: 처음에 "행 높이가 들쭉날쭉"이라고 적었으나 실측은
82~88px, 6px 차이였다. '가입 미완료'와 '번호 확인 필요'는 동시에 붙지 못해(전자는 번호 없음,
후자는 번호 있음) 배지가 3개 이상 되는 조합이 실제로 잘 안 나온다. **목록에서 고칠 것은 높이가
아니라 읽히는 방식이다.**

## 2. 목표와 비목표

### 목표
1. 회원을 **현황 5단**으로 갈라 보고, 분포를 숫자로 본다.
2. 한 사람을 열면 **무엇을 했는지 시간순으로** 5초 안에 파악한다.
3. **내가 아는 것을 남긴다**(메모·태그).
4. 반복해 거르는 조건에 **이름을 붙여 저장**하고, 걸린 사람을 **할 일로 뽑는다**.

### 비목표 (YAGNI — 대기업 것 중 안 한다)
- **감사 로그**(누가 언제 무엇을 고쳤나) — 관리자가 오너 한 명이다.
- **권한 세분화**(역할별 화면 제한) — 같은 이유.
- **자동 문자·메일 발송** — 운영이 카톡 오픈챗이라 겹친다.
- **리드 스코어링·마케팅 자동화** — 1,200명 규모에 과하다.
- **회원 삭제 버튼** — 기존 금지 유지. `members` 행만 지우면 `auth.users` 가 남아 그 사람이
  다시 로그인해도 프로필이 복구되지 않는다(`handle_new_user` 는 첫 로그인 한 번뿐). 보관이 정답이다.

## 3. 회원 현황 5단

오너 확정: 5단, **무료(재학생) 신청도 '고객'**.

| 등급 | 뜻 | 판정 |
|---|---|---|
| **고객** | 돈이 오간 사람 | 환불되지 않은 `appPaid` 또는 `appFree` 신청 1건 이상 · 또는 `credit_ledger` 에 `reason='purchase'` 인 줄(=충전 — `admin_grant` 는 오너가 준 것이라 제외) · 또는 `program_enrollments` 행 |
| **참여** | 돈은 안 냈지만 실제로 쓰는 사람 | `challenge_submissions` · `answers` · `credit_ledger` 사용(`delta<0`) 중 하나라도 있음 |
| **관심** | 번호를 남겼거나, 신청은 했는데 아직 안 씀 | 전화번호 있음 **또는 신청 이력 있음(미입금 포함)** + 위 둘 아님 |
| **가입만** | 로그인만 하고 프로필도 안 채움 | 번호 없음 + 가입 30일 이내 |
| **흔적 없음** | 정리 대상 | 번호 없음 + 신청·크레딧 사용 없음 + 30일 지남 (**현행 `ghost` 규칙 그대로 — `GHOST_DAYS=30`**) |

**위에서부터 먼저 걸리는 것이 이긴다**(고객 → 참여 → 관심 → 가입만 → 흔적 없음). 한 사람은
한 등급만 갖는다.

**환불만 있는 사람**: `appPaid` 는 `payment_status='refunded'` 도 true 로 본다(돈이 한 번은
움직였다는 뜻). 등급 판정에서는 **환불되지 않은 신청만** 센다 — 전액 환불하고 떠난 사람이
'고객'으로 남으면 진성 숫자가 부풀기 때문이다. 그런 사람은 활동에 따라 참여/관심으로 내려간다.

**'번호 확인 필요'·'기수 미배정'·'보관함'은 등급이 아니다.** 셀렉트 안에서 묶음을 갈라 둔다.

⚠️ **구현하며 두 번 막은 것**(둘 다 '보관 대상으로 잘못 떨어지는' 사고다):
- **`free_use` 는 delta 0 이다**(`20260725130000_credits.sql` 의 check 제약 — 무료분은 지갑에
  들어오지 않고 0짜리 한 행으로만 남는다). `delta<0` 만 '사용'으로 보면 **무료 한도만 쓴 회원이
  '흔적 없음'으로 떨어진다.** 판정은 `delta < 0 || reason = 'free_use'`.
- **'관심'에 '신청 이력'을 넣은 이유**: 구 ghost 규칙은 `!apps` 였다. 이걸 빼면 **번호 없이
  미입금 신청만 한 사람이 '흔적 없음'** 이 된다 — 지워도 되는 계정이 아니라 받아야 할 돈이다.

## 4. 화면 구조

### 4.1 사이드바

```
회원 (1,204)
[검색]
[회원 보기]  ← 셀렉트 1개, optgroup 4묶음
             현황: 전체·고객·참여·관심·가입만·흔적 없음
             확인 필요: 번호 확인 필요·기수 미배정
             저장한 조건: (사용자가 만든 것들) · + 지금 조건 저장…
             치워 둔 곳: 보관함 N
[회원 현황]  ← 분포. 등급별 인원 + 최대값 기준 비례 막대. 읽기 전용
[목록]
[더 보기]
[일괄 바]    ← 고른 게 있을 때만 나타남
▸ 기수 관리  ← 접이
```

- **분포는 읽기 전용이다.** 누르면 필터되게 만들지 않는다 — 고르기는 셀렉트 하나로 유지한다
  (같은 일을 두 벌로 두지 않는 규칙. 구 '미배정만' 체크박스 전례).
- **'흔적 없는 계정' 3문단 설명은 그 등급을 골랐을 때만** 목록 위에 뜬다. 늘 떠 있을 이유가 없다.
- **기수 추가 폼은 접이(`▸ 기수 관리`)로 내린다.** 매일 하는 일이 아니다.
- 막대는 **최대값 기준 비례**다. '가입만'이 압도적이면 그렇게 보여야 한다 — 그 사실 자체가
  오너가 알아야 할 값이다. 보기 좋으라고 비율을 조작하지 않는다.

### 4.2 목록 행

```
김승무                          8월 19일
seungmu.kim@example.com
MONC 1기  [고객]
```

- 이름 줄 오른쪽에 **마지막 움직임 날짜**. 아래 줄은 기수 + 등급 라벨 하나.
- 예외 하나: **'번호 확인 필요'는 빨간 라벨을 하나 더 단다**(고쳐야 할 값이라서).
- 오너·관리자 표시(`.madm`)는 그대로.
- 실측: 7행 전부 88px 동일(1280px). 가로 넘침 0(1280·375px).

## 5. 활동 타임라인 (DB 변경 없음)

이미 있는 데이터를 시간순으로 합쳐 그린다. **새 표를 만들지 않는다.**

| 종류 | 출처 | 시각 | 문구 |
|---|---|---|---|
| 가입 | `members.created_at` | 〃 | 가입 |
| 신청·입금 | `applications.created_at` | 〃 | `<챌린지> · <금액>원 · 입금 완료/아직 미입금/환불됨` |

| 제출물 | `challenge_submissions.created_at` | 〃 | `<챌린지> 처음/끝` |
| 답변 | `answers.updated_at` | 〃 | `"<문항>" 저장` |
| 크레딧 | `credit_ledger.created_at` | 〃 | `<tool> <delta>` |
| 자료 | `lab_downloads.created_at` | 〃 | `<자료명> 받음` |

- **최신 순.** 기본 20줄 + `[더 보기]`.
- ⚠️ **신청과 입금을 두 줄로 쪼개지 않는다.** `applications` 에 `paid_at` 컬럼이 **없어서**(실측)
  두 줄이 같은 시각에 찍힌다 — 화면이 거짓말한다. 한 줄에 입금 여부를 적는다.
- **마지막 움직임** = 이 목록의 첫 줄 시각. 목록 행·머리에 쓰는 값이 여기서 나온다.
- 표가 없거나(`PGRST205`) 조회가 실패한 종류는 **조용히 빼되, 패널 아래 한 줄로 사실대로
  적는다**("자료 받은 기록을 읽지 못했습니다"). 없는 것을 '없음'으로 단정하지 않는다.

## 6. 메모·태그 (마이그레이션 필요)

### 표

```
member_notes
  id uuid pk
  member_id uuid not null references members(id) on delete cascade
  body text not null
  created_by uuid references members(id)
  created_at timestamptz default now()

member_tags
  member_id uuid not null references members(id) on delete cascade
  tag text not null
  created_at timestamptz default now()
  primary key (member_id, tag)
```

### RLS — 관리자 전용

**두 표 모두 `authenticated` 에 일반 정책을 열지 않는다.** 회원 본인도 못 읽는다 — 상담
메모는 회원에게 보이면 안 되는 내용이 들어간다. admin 판정은 기존 `public.is_admin()` 을 그대로 쓴다
(2026-07-03 `20260703120000_membership_schema.sql` 에서 생성 — 재사용).

⚠️ 이 표는 **개인정보다.** 값은 레포에 넣지 않는다(CLAUDE.md '개인정보·학원 자산 반입 금지').

### 화면
- 태그는 **radius 4 네모 라벨**(알약 금지 — 2026-08-22 전 탭 규칙). `+ 태그` 는 점선 테두리.
- 메모는 최신 순, 작성자·날짜 + 본문. 입력칸 + `[메모 저장]`.
- 메모 본문은 `esc()` 로 넣는다.
- 표 미생성이면 패널이 "메모 기능이 아직 켜지지 않았습니다 — `<파일명>` 을 실행해 주세요"로
  degrade 한다(현행 보관 기능과 같은 방식).

## 7. 조건 저장(세그먼트) (마이그레이션 필요)

### 표

```
member_segments
  id uuid pk
  name text not null
  rule jsonb not null      -- 아래 형태
  created_by uuid references members(id)
  created_at timestamptz default now()
```

RLS 관리자 전용(6절과 동일).

### 조건 표현

`rule` 은 **AND 로 묶인 조건 배열**이다. OR·괄호는 넣지 않는다 — 필요해진 적이 없고,
넣는 순간 화면이 질의 편집기가 된다.

```json
{ "all": [
  { "k": "tier",    "v": "pay" },
  { "k": "cohort",  "v": "<cohort_id>" },
  { "k": "unpaid",  "v": true },
  { "k": "noSub",   "v": true },
  { "k": "idleDays","op": ">=", "v": 30 },
  { "k": "tag",     "v": "상담함" }
] }
```

`tier` 값은 현황 키(`all`·`pay`·`use`·`warm`·`new`·`ghost`)이지 한글 라벨이 아니다.

지원하는 `k` 는 위 6개다(`COND_KEYS`). 모르는 `k` 는 **조용히 무시하지 않고 그 조건을 못 건 채로
표시한다**("이 조건 중 1개를 읽지 못했습니다") — 조용히 무시하면 명단이 실제보다 넓어진다.

### 화면
- 셀렉트 `저장한 조건` 묶음에 이름 + 인원. 고르면 그 조건으로 목록이 걸린다.
- `+ 지금 조건 저장…` 은 지금 걸린 조건에 이름을 붙여 저장한다.
- 저장한 조건은 **수정·삭제 가능**. 삭제는 빨간 글자(현행 admin 규칙).

## 8. 후속 조치 목록

세그먼트에 `followup: true` 를 켜면 **'오늘' 탭 '지금 처리'에 한 줄로 올라간다.**
켜고 끄는 자리는 사이드바 '조건 더 걸기' 안의 체크박스다 — **저장한 조건을 고른 때만** 보인다.

- 문구는 **실측 숫자로만** 만든다(현행 '오늘' 규칙 그대로 — 없는 사실을 지어내지 않는다).
  예: `고객인데 30일 무소식 11명` → 누르면 회원 관리 탭 + 그 조건.
- 기존 3줄(입금 → 연락 → 검수)**아래에** 붙인다. 돈이 걸린 것이 먼저라는 순서를 바꾸지 않는다.
- `activateTab()` 로 이동한다(기존 숫자 클릭과 같은 경로). focus 값은 `seg:<id>`.
- ⚠️ 인원을 세는 `segFollowups()` 는 **화면에 걸린 조건(`_cond`)을 건드리지 않는다** — 세고 나서
  되돌린다. 안 그러면 '오늘'을 그릴 때마다 사용자가 보던 조건이 통째로 바뀐다.
- ⚠️ 자료가 아직 없으면(`tierReady()` false) **줄을 만들지 않는다.** 0명이라고 적으면
  "할 일이 없다"는 거짓말이 된다.

## 9. 데이터 조회와 성능

현재 진입 한 번에 테이블 조회 33회(회원 3,000 · 신청 1,500 기준). 이 개편으로 늘어나는 것:

| 무엇 | 언제 | 늘어나는 조회 |
|---|---|---|
| `member_segments` | **부팅** | +1 |
| 회원 자료(크레딧·활동) | 부팅 — **followup 켠 조건이 있을 때만** | 0 또는 +5 |
| `challenge_submissions`(member_id, created_at) | 회원 탭 로드 | +1 |
| `answers`(member_id, updated_at) | 회원 탭 로드 | +1 |
| `program_enrollments`(member_id) | 회원 탭 로드 | +1 |
| `member_tags`(전량 — 태그 조건용) | 회원 탭 로드 | +1 |
| `lab_downloads`·`member_notes`·`member_tags` | **회원을 고를 때만** | 상세당 +3 |
| `lab_resources`(제목) | 받은 기록이 있을 때만 | 상세당 +0~1 |

→ **부팅 33 → 34회**(후속 조치를 안 켰으면). 회원 관리 탭을 열면 +4.
`lab_downloads` 는 타임라인에만 쓰므로 목록 로드에서 뺐다 — 등급 판정에 안 들어간다.

- 목록용 조회는 **필요한 컬럼만** 뽑는다(본문·파일 경로를 받지 않는다). 단 신규 컬럼을 나열해
  미적용 환경에서 400 이 나지 않도록, **새 표는 `select('*')`**, 기존 표는 이미 있는 컬럼만 나열한다.
- 전량 조회는 전부 `fetchAll()`(1000행 절단 방지). **조용히 자르지 않는다** — 잘리면 빨간 한 줄.
- 목록은 `M_PAGE=100` 유지. 타임라인은 20줄 + 더 보기.
- 등급 계산은 회원마다 `_apps` 를 훑지 않는다 — **Map 인덱스를 한 번 만들어 O(1) 조회**
  (현행 `buildAppIndex()` 와 같은 방식. 3,000 × 1,500 = 450만 번 훑기 재발 금지).

## 10. 미적용·실패 시 동작

- 표 미생성 판정은 **`PGRST205`**(42P01 아님).
- 새 표 3개(`member_notes`·`member_tags`·`member_segments`)가 없어도 **나머지는 전부 정상
  동작한다.** 해당 패널·묶음만 안내 문구로 바뀐다.
- 조회 실패를 전부 '마이그레이션 미적용'으로 단정하지 않는다 — 네트워크·권한 오류를
  "SQL 을 실행하세요"로 안내하면 엉뚱한 곳을 고치게 된다.
- **근거를 못 받았으면 '없다'고 말하지 않는다.** 등급 판정에 필요한 자료가 아직 안 왔으면
  "판단할 자료를 받는 중입니다…"(현행 ghost 처리와 같은 규칙).

## 11. 코드 규칙

- **새 id 접두사**(2026-08-22 충돌 확인 — 전부 미사용): 타임라인 `mlog` · 메모 `mmemo` ·
  태그 `mtag` · 세그먼트 `mseg`. CLAUDE.md 의 접두사 목록에 이 4개를 추가한다.
  ⚠️ `mt` 는 모바일 상단 바(`mtCur`·`mtMenu`·`mtop`)가 이미 쓰고 있다.
- **알약 금지** — `border-radius:999px` 0곳 유지. 상태·태그 라벨은 radius 4, 행 동작은 네모
  버튼, 삭제는 빨간 글자, 목록은 구분선 한 판(2026-08-22 전 탭 규칙).
- `.prow` 는 회원 정보 폼에서 폐기하고 **2열 그리드**로 바꾼다. 다른 탭에서 `.prow` 를 쓰는
  곳이 있으면 그대로 둔다(회원 상세만 바꾼다).
- 회원 선택은 `role`·`tabindex`·Enter/Space 한 벌 유지(div+click 금지).
- 사용자·회원이 쓴 문자열은 전부 `esc()`.
- 보관 대상에서 오너·관리자 제외 — 현행 유지.

## 12. 단계

오너 확정: **3단계 전부.** 단계는 배포 단위다 — 각 단계 끝에서 화면이 온전해야 한다.

| 단계 | 무엇 | 오너 작업 |
|---|---|---|
| **1** | 사이드바·목록·상세 재배치 + 회원 현황 5단 + 분포 + **활동 타임라인** | 없음 |
| **2** | **메모·태그** | SQL 1회(`member_notes`·`member_tags`) |
| **3** | **조건 저장 + 후속 조치 목록** | SQL 1회(`member_segments`) |

1단계는 DB 를 건드리지 않으므로 먼저 올려도 안전하다.

## 13. 검증

이 레포엔 lint·build·테스트 시스템이 없다. 검증 수단은 아래가 전부다.

1. **브라우저 실측 — 375px 우선**, 1280px 도 같이. 가로 넘침 0.
2. **목록 행 높이 동일** — `[...document.querySelectorAll('.mitem')].map(e=>e.getBoundingClientRect().height)`.
3. **등급 판정 대조** — 분포 5단 합 + 보관 수 = 전체 회원 수. 어긋나면 등급 규칙에 구멍이 있다.
4. **표 미생성 degrade** — 새 표 3개가 없는 상태에서 탭을 열어 콘솔 에러 0 · 나머지 패널 정상.
5. **조회 수** — 진입 시 네트워크 요청을 세어 38회 이내.
6. admin 은 로그인이 필요하므로, 기존 방식대로 `requireAdmin`·`MONC.sb` 를 목으로 바꾼
   `admin-preview.html` 사본으로 확인한다(**커밋 금지**).

## 14. 열린 질문

- **태그 목록을 고정할지 자유 입력할지.** 자유 입력이면 오타로 갈라진다("대한항공"/"대한항공사").
  1차는 자유 입력 + 기존 태그 자동완성으로 두고, 갈라지면 그때 고정 목록으로 좁힌다.
- **메모 작성자** — 지금은 오너 한 명이라 `created_by` 가 늘 같다. 표에는 넣되 화면에는
  관리자가 둘 이상일 때만 이름을 띄운다.
