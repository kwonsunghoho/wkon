# Supabase 변경·적용 절차

DB·Edge Function을 변경하거나 배포할 때 읽는다. 기능별 판정 규칙은 해당 기능 문서, **현재 적용 상태와 함수 버전은 `docs/notes/implementation-status.md`**가 원장이다.

## DB·마이그레이션

- 테이블·RLS·컬럼 변경은 `supabase/migrations/`에 기록한다. 파일을 커밋해도 운영 DB에는 적용되지 않으며, 오너가 Supabase SQL Editor에서 실행해야 한다.
- 실행 안내 전에 적용 상태와 최근 마이그레이션을 확인한다. 이미 적용된 변경을 새 작업으로 오인하거나 다시 실행하게 하지 않는다.
- **미적용 환경에서도 조용히 동작을 줄여야 한다.** 목록 조회는 `select('*')`를 사용한다. 신규 컬럼을 나열하면 미적용 환경에서 400이 발생하므로 `getMyProfile()` 같은 공용 조회에도 추가하지 않는다.
- 테이블 미생성의 PostgREST 오류 코드는 **`PGRST205`**다. `42P01`만 검사하지 않는다.
- SQL은 파일 경로 대신 대화창의 `sql` 코드 블록으로 실행할 본문을 제공한다. 비공개 자료·개인정보를 담은 데이터 입력 SQL은 공개 레포에 저장하지 않는다.

## Edge Function

- **배포는 Supabase 콘솔에서 한다.** 오너에게 `supabase functions deploy`를 안내하지 않는다. 대시보드 → Edge Functions → 함수 선택 → 코드 전체 교체 → Deploy 순서와 파일 링크를 제공한다.
- 콘솔에 붙여넣어 배포하므로 **함수는 한 파일을 유지**한다. 모듈로 분리하지 않는다.
- 코드를 고치면 **`FN_VERSION`도 올린다.** 새 함수에는 처음부터 `FN_VERSION`과 `probe:true` 분기를 넣으며, 프로브 분기는 인증 검사보다 앞에 둔다.
- 배포 여부는 **anon key 프로브로 직접 확인**한다. 버전 확인을 위해 오너에게 SQL을 실행하게 하지 않는다. 프로브에는 비밀값이나 개인정보를 내보내지 않는다.
- **`portone-webhook`만 콘솔의 JWT 검증을 끈다.** 포트원 통보에는 Supabase 키가 없기 때문이다. 다른 함수의 JWT 검증을 끄지 않는다.

## 적용 완료

- 오너 작업은 실행 순서·누를 메뉴·복사할 내용·완료 기준으로 따로 안내한다. 상세 전달 방식은 `docs/notes/working-rules.md`의 '오너에게 안내할 때'를 따른다.
- 로컬 변경·SQL 실행·함수 배포를 구분하고, 실제 확인한 결과만 `docs/notes/implementation-status.md`에 갱신한다. 적용되지 않은 상태를 완료로 기록하지 않는다.
