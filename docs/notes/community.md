# 게시판·스터디·스터디 프로필

## 작업 전 핵심 규칙

- **2026-10-14 명칭 확정**: 공간 전환은 면접 연구소 / 승준 커뮤니티. 커뮤니티 홈 제목은 승준 커뮤니티, 설명은 "승준생끼리 묻고 답하고, 스터디로 함께 준비해요."다. 최근 목록은 "최근 올라온 글", 모집 목록은 "모집 중인 스터디"로 표시한다. 연구소 진입은 챌린지 단독 주소가 아닌 `index.html`이다.
- `community.html` + `community.css` + `community.js`. 기본 진입은 커뮤니티 홈이며 하단 메뉴는 홈 / 게시판 / 스터디 / 내 활동이다. 내 프로필은 내 활동에서 연다. 소개 홈은 유지하고 진입·미리보기만 추가한다(home.md).
- 게시판 주제 `topic`은 승준정보(prep) / 헤메&샵(hair) / 자유게시판(free), 글 종류 `category`는 질문 / 정보 공유 / 자유글이다. 두 항목을 별도로 선택·저장하며 검색·페이지 이동 후 필터는 주소에 보존한다. 이전 요청처럼 topic이 없으면 새 글은 승준정보(자유글은 자유게시판), 수정은 기존 주제를 유지한다.
- 글·댓글·모집글은 비회원도 읽는다. 글쓰기·지원·프로필·내 활동은 기존 `MONC.requireConsent()`를 통과한 회원만 사용한다. 서버도 회원·동의 기록·연락처 유무를 검사한다.
- 기존 `members`의 실명·전화번호 접근 범위를 바꾸지 않는다. 연락처 변경은 계속 `MONC.saveMyProfile()`만 사용한다. 커뮤니티 프로필은 별도 비공개 원장과 `community_member('profile-save')`로 저장한다.
- 준비 항목은 **본인 표시**, 평가 항목은 **몬크 확인**으로 구분한다. 경험 인증과 실력검증은 독립적이다. 수강 이력만으로 실력 뱃지를 자동 부여하지 않는다.
- 인증 원본·샘플·참여자 안내는 공개 테이블/레포에 넣지 않는다. `community-private`은 비공개 버킷이며 브라우저에 Storage 쓰기·목록 권한을 주지 않는다.
- 승인·반려 후 원본의 만료일을 30일 뒤로 지정한다. 만료 즉시 열람을 차단하고 매시간 정리한다. 원본이 없어져도 인증 결과는 유지한다. 미제출 업로드는 7일 후 정리하고, 대기 중 신청은 심사 전 임의 만료시키지 않는다. 철회·계정 파기 시 즉시 열람을 막고 정리 대상으로 넘긴다.
- UI 승인 전 main 푸시를 하지 않는다. 현재 운영 적용 여부는 implementation-status.md가 원장이다.

## 데이터·권한

원장은 비공개 `monc_community` 스키마에 있다. 모든 표에 RLS를 켜고 anon/authenticated의 스키마·표 직접 접근을 회수한다. 제한된 `SECURITY DEFINER` 함수만 반환 항목을 고르며 `search_path=''`를 사용한다.

| 창구 | 권한·역할 |
|---|---|
| `community_read` | 비회원·회원. 공개 글/댓글 검색, 커서 목록, 모집 상세. 계정 UUID·원본 경로·참여자 안내를 반환하지 않는다. |
| `community_member` | 동의한 회원. 자신의 프로필/글/댓글/저장/신고/지원/내역, 회원용 프로필, 지원 관계에 따른 샘플 메타데이터. |
| `community_admin` | 기존 `members.role=admin`을 서버에서 확인. 원본 심사, 평가 등록·취소, 인증 취소, 신고 숨김·종결, 이용 제한. |
| 파일 보조 RPC | service_role 전용. 확인된 사용자 UUID를 받아 실제 소유권·범위를 다시 확인한다. |

검색은 글 제목·본문과 공개 댓글의 부분 문자열을 찾는다. 항공사/전형은 선택 입력이며 출처는 HTTPS 링크만 저장한다. 글 수정으로 운영진이 숨긴 상태를 공개로 되돌릴 수 없다. 삭제는 본문을 지우고 상태를 바꾸며 타인의 댓글 관계는 보존한다.

실력 레벨은 운영진이 수업 평가 또는 레벨테스트 결과로 Lv.1 기본 준비 / Lv.2 실전 대응 / Lv.3 스터디 리딩을 수동 등록한다. 확인한 항목·평가일·선택 유효기간을 표시한다. 평가지·가격·예약 기능은 이번 코드에 넣지 않았다. 레벨의 평가 기준과 교육 운영은 몬크 운영진이 정한다.

## 스터디

- 2~12명, 모집자 포함. 실력 레벨·경험 인증·본인 표시 항목을 조건으로 지정한다. 모집자도 같은 조건을 충족해야 등록할 수 있다.
- 지원·참여 승인 시 서버가 조건을 재검사한다. 스터디 행을 잠근 뒤 정원·중복을 판단한다. 지원만으로 인원을 차감하지 않는다.
- 모집자는 소개·일정·정원을 수정할 수 있지만 현재 인원보다 정원을 줄이거나 기존 참여자가 충족하지 못하는 조건으로 바꾸지 못한다.
- 지원 상태: pending / accepted / rejected / withdrawn / closed. 중복 대기 지원은 기존 요청을 반환한다. 모집 종료는 대기 지원을 종료하고 이미 구성된 팀은 유지한다.
- 모집자 인계는 현재 참여자에게만 가능하다. 모집자는 인계 전 나갈 수 없다. 탈퇴한 모집자의 스터디는 종료하고 본문·장소·참여자 안내를 지운다.
- `member_guide`는 모집자가 작성하고 승인된 참여자와 모집자만 읽는다. 공개 모집글·일반 회원의 상세 조회에는 넣지 않는다.
- 카드의 인증 인원은 현재 참여자의 인증을 집계한다. 이를 스터디 자체에 대한 몬크 보증으로 표현하지 않는다.

## 파일·인증

- `community-file/index.ts` 단일 파일. JWT를 Auth에서 검증하고, 파일 접근은 서버 RPC로 재검사한다. 일반 JWT를 서비스 권한으로 판단하지 않는다.
- 원본: PDF/PNG/JPEG 8MB, 텍스트: UTF-8 txt 40KB·10,000자, 음성: MP3/WAV/M4A/WebM 20MB, 영상: MP4/WebM 40MB. 파일명·확장자만 믿지 않고 바이트 형식을 검사한다.
- 파일은 사용자 UUID/무작위 UUID로 저장하고 덮어쓰지 않는다. 원장을 먼저 등록하며 업로드 실패 시 만료 처리하여 실제 파일 유무를 정리 작업에서 다시 확인한다. 서명 링크는 60초다.
- 샘플 범위: 나만 / 내가 지원한 스터디 모집자 / 회원. 모집자 범위는 실제 pending·accepted 지원 관계로 판단한다. 지원 철회·거절·스터디 탈퇴 후에는 접근이 끊긴다. 권한 없는 샘플의 제목도 프로필에 내보내지 않는다.
- 경험 인증은 운영진이 회원 이름·항공사·연도·전형·자료를 확인한 뒤 승인한다. 승인과 뱃지 생성은 같은 DB 작업이다. OCR·자동 진위 판독은 구현하지 않았다.
- 원본 정리는 service_role 자격과 Vault를 사용하는 예약 함수로만 실행한다. 한 번에 100개씩 최대 10묶음. Storage 삭제 성공 후 DB에 삭제 기록을 남긴다. 실패한 기록은 다음 실행 때 재시도할 수 있다. 서류 본문·경로·JWT를 로그에 남기지 않는다.

## 화면·검증

입력 화면이므로 bfcache 복귀 때 전체 새로고침하지 않는다(page-common의 입력 화면 예외). 버튼·세션·동의를 재확인하며 계정 변경 시 이전 프로필/입력 창을 닫는다. 공용 nav·인앱 안내·정적 OG 메타를 사용한다. 관리자 운영 메뉴와 마이페이지의 내 스터디 프로필에서 진입한다.

검증용 `scripts/community-preview-server.mjs`는 로컬 메모리 PostgreSQL을 사용한다. 운영 SDK CDN·supabase-config.js를 HTML에서 제거하고 가짜 MONC로 대체한다. 네트워크·회원 데이터는 운영과 분리된다. 브라우저용 파일 모형은 UX 확인용이며 파일 형식 검사는 실제 Edge 소스를 실행하는 아래 검사로 확인한다. 검증용 HTML 사본은 따로 저장하지 않는다.

```text
node scripts/community-tests.mjs --deps <임시 PGlite 설치 경로>
node scripts/community-file-tests.mjs
node scripts/community-preview-server.mjs --deps <임시 PGlite 설치 경로> --source <레포 루트>
```

테스트 의존성 `@electric-sql/pglite@0.5.9`는 레포 밖 임시 경로에 설치한다. package.json·번들러를 새로 만들지 않는다. DB 검사는 실제 PostgreSQL에서 ACL·상태·탈퇴를 실행하고, 예약 검사는 pg_net/cron 송신 부분만 모형으로 대체한다. 파일 검사는 실제 함수 요청 처리에 Auth/Storage 모형을 주입한다. Deno가 없는 환경에서는 타입 검사 미실행을 보고한다.

## 운영 적용 순서

화면 승인 후 진행한다. 이 문서는 적용 완료를 뜻하지 않는다.

1. MONC 프로젝트(`apzwauiumhmsvrgffjis`) → SQL Editor에서 `20261013090000_community.sql` 전체를 실행한다. 기존 스키마가 없을 때 최초 1회 적용한다. 성공 후 비공개 스키마·버킷·RPC가 생성되어야 한다.
2. Edge Functions → `community-file` 새 함수 → `index.ts` 전체를 붙여넣고 Deploy. JWT 검증을 켠다. 에이전트가 anon 프로브로 `2026-10-13a`를 확인한다.
3. SQL Editor에서 `20261013091000_community_cleanup.sql`을 실행한다. 기존 Vault의 `monc_lab_cleanup_service_role`을 사용하므로 비밀값을 대화·레포에 복사하지 않는다. 예약 작업과 HTTP 결과에서 실패가 없는지 확인한다.
4. 사이트를 main에 반영한 뒤 에이전트가 운영 주소에서 비회원 목록·로그인 동의·관리자 게이트를 확인한다. 회원 쓰기·서류 업로드·최종 심사는 오너의 실제 계정으로 확인한다.

오너에게 실행을 요청하는 시점에는 working-rules에 따라 SQL을 대화창 코드 블록으로 제공하고 긴 함수는 파일 링크로 제공한다. 연결 도구에 다른 프로젝트만 보이면 그 프로젝트에 적용하지 않는다.
