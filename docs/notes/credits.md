# 답변 저장소 + 크레딧 — 상세 기록

## 단위 표기 — 크레딧은 '개', 사용 횟수만 '회' (2026-08-06 오너 지적)

오너 지적: *"가입축하, 크레딧충전을 회라고 이야기하니까 뭔가 어감이 안맞아. 갯수로 표현하는게 맞지않나?"*

크레딧은 **개수**이고 '회'는 도구를 몇 번 쓰느냐다. 두 뜻이 한 화면에서 같은 단위로 붙어 있었다 —
충전 상품 이름이 `30회`인데 바로 아래 환산이 `검사 10회`라, 같은 '회'인데 숫자가 셋 배 차이 났다.

- **크레딧 개수 = '개'**: 회원 잔액, 지급·회수, 충전 상품 개수, 가입 축하.
- **도구 사용 횟수 = '회'**: '검사 10회', '오늘 3회 무료', '무료 사용 3회', '1회 쓸 때 빠지는 크레딧'.
- ⚠️ **`credit_packs` 에 `label` 을 저장하지 않는다.** 전에는 admin 이 `label: count + '회'` 를
  같이 넣었는데, 이름을 저장해 두면 단위를 고쳐도 옛 이름이 화면에 계속 뜬다. 상품 이름은
  화면이 `count + '크레딧'` 으로 짓는다(ai-killer 충전함·mypage 지갑 같은 규칙). `verify-payment` 는
  `count`·`price`·`tool` 만 읽으므로 **함수 재배포는 필요 없다.**
- 결제창 상품명도 개수로: `몬크 AI킬러 크레딧 N개` · `몬크 크레딧 N개`.
- 남은 일: 프로덕션 `credit_packs` 행에 옛 `label` 이 남아 있어도 화면은 무시한다. admin
  '충전 상품 저장'을 한 번 누르면 데이터에서도 지워진다(선택).

## 가입 축하 크레딧 15 (2026-08-02 오너 "맛보기로 사용해볼 수 있도록" · "15크레딧으로 가자")

- migration `20260802100000_signup_credit.sql` — `site_config.credit_signup_bonus`(기본 15) + `grant_signup_credit()` RPC. **회원당 1회**, 부분 유니크 인덱스(`reason='admin_grant' and ref='signup'`)가 최종 방어라 멱등이다. 호출은 login.html `routeByRole()` 에서 매번 — 조건을 따지지 않는다(따지면 '동의는 했는데 못 받은 사람'이 생긴다). 이미 가입해 있던 회원도 다음 로그인에 한 번 받는다.
- **동의를 마친 회원(`members.agreed_at`)에게만** 준다 — 동의 거부 후 파기(`delete_my_account`) 대상과 원장이 어긋나지 않게.
- ⚠️ **하루 무료(5)는 그대로 둔다.** 하루 무료를 올리는 방식은 매일 반복돼 원가 상한이 없고, 첨삭 단가(10) 이상이 되는 순간 첨삭이 매일 공짜가 된다. 가입 축하는 인당 1회라 비용 상한이 고정 — 후하게 풀 땐 이쪽 값을 올린다(admin '크레딧' 탭 '가입 축하(1회)' 칸).
- 왜 15인가: 하루 무료 5 + 축하 15 + 첨삭 첫 1회 무료면 **첫날에 자소서 한 문항을 끝까지** 완성할 수 있다(소재 2 + 킬러 3×2 + 첨삭 10 ≒ 18). 값을 낮추면 중간에 끊겨 가치를 못 본다. **단가 인하로 대신하지 말 것** — 단가는 되돌릴 때 '요금 인상'이 되지만 축하 지급은 조용히 멈출 수 있다.

## 환급 RPC 서버 전용화 (2026-08-04 보안 점검)

**구멍**: `refund_credit(p_tool, p_ref)` 이 `authenticated` 에 grant 돼 있었다. 대상을 `auth.uid()` 로 정하는 함수라 에지 함수가 **사용자 JWT 로** 불러야 했고, 그래서 브라우저에도 열려 있었다. 로그인한 학생이 ① 유료 기능을 쓰고 결과를 받은 뒤 ② 본인 `credit_ledger` 를 select 해 차감 키(`ref`)를 읽고 ③ `POST /rest/v1/rpc/refund_credit` 을 부르면 크레딧이 그대로 돌아왔다. **유료 기능 전부가 사실상 무료·무제한**이 되는 상태였다. 무료분(`free_use`)은 행이 삭제되므로 하루 한도까지 복구됐다.

**고친 방식**: 대상 회원을 인자로 받는 `refund_credit_for(p_member, p_tool, p_ref)` 를 새로 만들고 **`service_role` 에만 grant**. 동작은 기존과 같다(유료=refund 행 추가·무료=free_use 행 삭제·같은 ref 이중 환급 방지·회원 단위 advisory lock). 에지 함수(`ai-killer`·`sojae-chat`)는 catch 에서 service_role 클라이언트를 새로 만들어 이쪽을 부른다 — 그래서 `charged` 가 `member` 를 같이 들고 다닌다.

**⚠️ 배포 순서**(어기면 학생이 크레딧을 잃는다): ① migration `20260804150000_rls_hardening.sql` → ② 두 함수 재배포(프로브 `features` 에 `refund_server` 확인) → ③ migration `20260804160000_refund_credit_lockdown.sql`(구 RPC 회수). ②를 건너뛰고 ③을 먼저 하면 AI 호출 실패 시 환급이 권한 없음으로 죽는다.

**2026-08-04 세 단계 모두 완료.** 권한표 실측 — `refund_credit` authenticated=false, `refund_credit_for` service_role=true, AI킬러 검사 1회로 차감 정상. `refund_credit` 의 service_role 은 true 로 남는데 정상이다(`revoke ... from public` 은 service_role 에 준 권한을 회수하지 않는다 — 서버 전용 키라 브라우저에 안 나간다).

`spend_credit` 은 그대로 `authenticated` 에 열어 둔다 — 직접 불러 봐야 자기 크레딧만 깎이고, 환급 길이 막히면 얻는 게 없다.

### 답변 저장소 + 크레딧 (2026-07-25 재설계 — 구조가 뒤집혔다)

**구조의 중심은 AI킬러가 아니라 `answers`(답변 저장소)이고, KILL AI 는 그 위에서 도는 기능이다.**
오너 지적: *"소재발굴을 하지 않고 그냥 바로 답변을 넣고싶은 애들도 있다. 소재 발굴은 소재를 발굴하는 곳이지 답변을 넣는 관문이 아니다."*

- **글이 저장소로 들어오는 길 셋 — 전부 열어 둔다**: ① `answers.html` 에서 직접 쓰기(무료·무제한) ② 소재 발굴 ③ **KILL AI 에 붙여넣으면 서버가 자동 저장**. ⚠️ 어느 길도 막지 말 것 — 특히 소재 발굴을 관문으로 만들지 말 것.
- **⚠️ 저장은 언제나 무료·무제한.** 크레딧과 무관하다. 화면에도 "무제한 무료"를 명시한다(검사 횟수가 없으면 저장도 못 하는 줄 아는 오해가 실제로 생긴다).
- **크레딧 차등**: 소재 발굴 **2** / KILL AI **3** / 첨삭 **10**. ⚠️ **가격은 원가가 아니라 가치를 따랐다** — 첨삭 원가는 킬러의 두 배쯤인데 단가는 세 배다. 학생이 돈을 내는 이유가 진단이 아니라 처방이라서다. **진단이 싸야 자주 쓰고, 자주 써야 처방 결제로 이어진다.** 원가 비율로 되돌리지 말 것. **첨삭은 2026-07-30 실제 출시**(그 전까지는 가격표·admin 칸만 있고 코드가 없어 동작하지 않는 상품이었다 — 아래 `polish.html` 항목 참조).
- **무료 = 하루 5크레딧(소재 1회 + 킬러 1회), 쌓이지 않고 리셋.** *(설계 기본값 — 실제 값은 2026-07-27부터 admin '크레딧' 탭에서 조절한다. 아래 소재 발굴 항목 참조.)* ⚠️ **이 리셋이 곧 첨삭 잠금이다** — 하루 5로는 첨삭 10을 못 모으므로 별도 free/paid 구분이 필요 없다(첨삭이 5크레딧이던 시절 계산을 그대로 들고 와 잠금을 넣었다가 오너 지적으로 걷어냈다). 첨삭만 **가입 후 총 1회** 무료(`credit_free_limits`) — 한 번은 봐야 값어치를 알고, 안 보면 결제할 이유가 없다.

### ⚠️ 총량 무료 폴백 — 설정에서 빼도 안 막힌다(2026-08-06 발견)

`credit_free_limit(p_tool)` 은 `credit_free_limits` 에 그 도구 키가 **없으면** 함수 안 폴백
`case p_tool when 'ai_killer' then 2 when 'rehearsal' then 1 else 0 end` 를 돌려준다.
그래서 `20260725180000` 이 설정에서 `ai_killer` 를 뺐는데도 **한도가 0 이 아니라 2** 다
(프로덕션 실측: `credit_free_limits` = `{"polish": 1}`).

`spend_credit` 은 `v_free_lim > 0` 만 보고 총량 무료 분기를 열고, `free_ref` 를
`coalesce(nullif(p_free_ref,''), p_ref)` 로 채운다 — **`p_free_ref: null` 로 불러도 막히지 않는다.**
결과: 회원마다 AI킬러 **첫 2회가 총량 무료로 나가고**, 그 위에 하루 무료 5가 또 붙는다.
`20260725180000` 주석이 "남겨 두면 하루 무료와 총량 무료를 둘 다 받아 첫 이틀이 공짜가 된다"고
막으려던 상황이 그대로 살아 있다.

- **막으려면 설정이 아니라 함수를 고쳐야 한다** — 폴백을 `case p_tool when 'polish' then 1 else 0 end`
  로 바꾼다(마이그레이션 `20260806120000_credit_free_limit_fallback.sql`).
  ⚠️ **이 마이그레이션은 2026-08-06 오너 결정으로 실행 보류다** — *"일단 둘게, 비용관련된건 나중에
  한번에 대대적으로 잡자"*. 임의로 실행하지 말 것. 비용 일괄 점검 때 같이 본다
  (목록은 `docs/notes/implementation-status.md` '비용 일괄 점검' 절).
- ⚠️ **새 도구를 폴백 case 에 추가하지 말 것.** 폴백은 '설정이 깨졌을 때의 안전값'이지 지급량
  조절값이 아니다. 무료를 늘리려면 admin '크레딧' 탭(설정)이나 `grant_credit` 일괄 지급을 쓴다.
- **⚠️ 차감 키(`spend_credit`의 `p_ref`)는 검사 id 가 아니라 `<answer_id>#<묶음>`** 이다. 같은 답변을 `MAX_RECHECK`(2회)까지는 같은 키로 부르므로 RPC 가 `already` 로 통과시켜 **재검사가 무차감**이 된다. 고치고 다시 확인하는 게 이 도구의 핵심 루프라, 재검사에 매번 받으면 학생이 확인을 안 해 도구가 반쪽이 된다. 3번째부터 묶음 번호가 올라가 새로 차감된다.
- **⚠️ 브라우저가 보낸 `answerId` 를 믿지 않는다.** 저장·수정이 service role 이라 RLS 를 통과하므로, 남의 답변 id 를 넣으면 그 사람 글이 덮인다. 소유 확인 후 **아니면 에러 대신 새로 저장**한다(에러로 막으면 '답변을 지운 뒤 뒤로가기' 같은 정상 사용까지 죽는다).
- **⚠️ 검사 뒤 저장소의 그 답변도 방금 검사한 글로 맞춘다** — 안 하면 다음 검사가 옛 글로 돌아간다.
- **⚠️ `free_use` 행에 `cost` 를 남긴다** — `delta` 가 0 이라 그것만으로는 하루 사용량을 셀 수 없다. **환급은 `cost` 만큼**(구 `+1` 고정이면 첨삭 10 실패에 1만 돌려주고 나머지 9는 돌려주지 않는다). 하루 경계는 **Asia/Seoul 자정**(UTC 로 두면 한국 오전 9시에 초기화된다).
- **분류 3종**(`answers.category`·`doc_kind`·`airline`): 유형은 **새로 만들지 않고** `questions.category` 4종을 그대로 쓴다 — 새 체계를 만들면 소재 발굴 답변과 직접 쓴 답변이 서로 다른 분류에 걸려 필터가 반쪽이 된다. ⚠️ `airline` 의 **`'all'`(만능)과 NULL(아직 안 정함)은 다른 값**이다(첨삭 방향이 갈린다).
- **⚠️ `answers.html` 과 `mypage.html` 은 같이 고친다** — 제목 폴백(`questions.content || title`)·분류를 한쪽만 고치면 직접 쓴 답변이 제목 없이 뜬다. 조회는 **`select('*')`** (컬럼을 나열하면 미적용 환경에서 목록 전체가 400).

## 2026-08-05 답변노트 — 빈 초안 안 만들기 · 개별 삭제 · 수정 이력 (오너 지시)

발단은 오너 신고 하나다. **"답변을 선택하고 나서 아무것도 안 썼는데도 답변노트에 저장이 된다."**
`sojae.html` 이 **첫 메시지를 보내는 순간** `content=''` 인 `answers` 초안 행을 만들고 있었다
(마이페이지 '작성 중'에 띄우려던 의도). 대화만 하다 나가면 내용 없는 항목이 노트에 남았다.

- **빈 글로는 행을 만들지 않는다.** `saveDraftAnswer()` 가 글이 비었고 저장된 행도 없으면 아무것도 쓰지 않는다.
  이미 저장된 행이면 지운 것도 반영한다(글을 다 지운 것도 편집이다). 첫 전송 시 호출은 삭제.
  ⚠️ **되돌리지 말 것** — 이어쓰기는 이 행이 없어도 된다. 대화·뼈대는 `discovery_sessions` 가 들고 있고,
  소재 발굴 진입 화면이 그 문제에 '이어쓰기'를 붙인다. 대신 마이페이지에 **'대화 중' 줄**을 새로 만들었다(mypage.md).
- **문제 선택은 API 를 부르지 않는다**(오너 질문에 대한 답). `startChat()` 은 배지 표시와 **하드코딩된 인사말**뿐이고,
  `sojae-chat` 호출은 ① 메시지 전송 ② 전구(도움) ③ 다듬기 세 곳뿐이다. 원가는 첫 메시지부터 발생한다.
- **개별 삭제** — 카드를 펼친 맨 아래 '삭제'. `confirm()` 한 번(사이트 관례 — 소재 카드 삭제와 같다) 뒤 하드 삭제.
  휴지통은 만들지 않았다(오너 선택). 검사·첨삭 기록은 `on delete set null` 이라 연결만 끊기고 남는다.
  ⚠️ 초안 카드는 **카드 전체가 링크였는데 `<div>` + 버튼 줄로 바꿨다** — `<a>` 안에 `<button>` 을 넣을 수 없다.
  ⚠️ `buildChips()` 를 삭제 뒤에도 부르므로 **클릭 핸들러는 한 번만 붙인다**(`buildChips.wired`). 두 번 붙으면 칩 한 번 눌러 두 번 처리된다.
- **수정 이력** — `answer_revisions` + `answers` UPDATE 트리거(마이그레이션 `20260805130000`).
  ⚠️ **화면마다 스냅샷을 심지 않는다.** 본문을 고치는 곳이 넷인데(소재 발굴·AI킬러 저장·첨삭 반영·답변 프로그램 확정)
  가운데 둘은 **서버 함수가 service role 로 직접 update** 한다 — 브라우저 코드로는 못 잡는다. 트리거가 유일한 단일 지점이다.
  ⚠️ **10분 묶기** — 소재 발굴은 0.8초 디바운스 자동 저장이라 묶지 않으면 이력이 수백 개가 된다.
  결과적으로 남는 것은 '고치기 시작하기 직전 원본' 한 벌. 답변당 20개 상한.
  ⚠️ 목록은 **본문 없이** `id, answer_id, created_at` 만 받는다 — 버전 본문은 그 버전을 펼칠 때 한 행만(`loadRev`). 전송량 예산.
  화면은 두 겹 접이(바깥 '수정 이력 N개' → 버전마다 날짜만). **지난 본문을 펼친 채로 늘어놓지 말 것**(오너 지시).
  되돌리기 버튼은 넣지 않았다 — 되돌리기 자체가 또 하나의 수정이라 이력이 꼬인다.

  ⚠️ 저장 뒤 **목록을 통째로 다시 그리지 않는다**(펼쳐 둔 카드가 닫히고 스크롤이 튄다). 본문·날짜만 갈아 끼우고,

  ⚠️ draft-keep(`data-keep`)은 안 붙였다 — 칸이 서버 본문으로 이미 차 있어 되살리기가 동작하지 않는다

- 서버 저장이 필요하면 `program.html` 처럼 해당 기능 테이블에 컬럼을 두고 마이그레이션을 쓴다.
- 값이 이미 있는 칸은 덮지 않는다(서버에서 불러온 초안 보호). 되살렸다는 사실을 화면에 말한다.
- 저장 성공 시 `moncDraftClear(key)` 로 지운다 — 안 지우면 다음에 빈 폼에서 되살아나
  중복 저장이 된다.
