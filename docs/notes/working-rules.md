# 작업 방식 규칙

오너가 작업 중에 직접 지시한 방식과, 같은 사고를 반복하지 않으려고 남긴 절차다. 2026-09-29 이전 도구(Claude Code)의 개인 메모리에 있던 것을 레포로 옮겼다. 기능 규칙이 아니라 **일하는 방법**만 다룬다 — 기능 규칙은 `AGENTS.md`의 '필요한 문서만 읽기' 표를 따른다. 아래에서 현재 작업에 필요한 절만 읽는다.

## 응답

- **모든 응답은 한국어.** 코드·식별자·불가피한 기술 용어만 예외. 커밋 메시지·코드 주석도 한국어.
- 결론 먼저 1~3문장, 근거는 판단에 필요한 만큼만. 비유·감정 표현·반복 설명을 뺀다.
- 선택지를 물을 때는 전문 용어·코드 맥락 없이 일상어로, **한 번에 1~2개까지.**

## 계획과 승인

- **계획을 썼으면 오너와 같이 검토한다.** 핵심 결정 사항을 요약해 보이고, 오너가 내용을 확인해 진행하라고 한 뒤에 구현한다(2026-07-18).
- **원인과 고칠 곳이 이미 특정됐으면 바로 고친다.** 설계안 비교·하위 에이전트 분산·다단 리뷰는 방향 자체가 갈리거나 코드를 넓게 훑어야 할 때만 쓴다(2026-07-16). 구현은 기본적으로 한 세션에서 직접 한다.
- **본뜰 기존 패턴이 애매하거나 후보가 둘 이상이면 오너에게 묻는다**(2026-07-30). 사소한 관례까지 묻지는 않는다.
- **UI 수정 순서: 구현 → 375px 목업·스크린샷 제시 → 오너 승인 → 커밋·main 푸시**(2026-08-06). 승인 전 푸시 금지. 이미 승인된 배포본의 명백한 결함 수정은 바로 올려도 된다. 글꼴·색 같은 브랜드 방향 변경은 따로 확정받는다.
- 승인된 범위의 구현·수정·검증은 이어서 진행한다. 같은 작업에 이미 받은 승인을 반복해서 요청하지 않는다.

## 작업 시작

- **새 코드 변경은 `git status`로 기존 변경을 확인하고, `git fetch origin main` 뒤 `origin/main` 기준 새 브랜치를 만든 다음 문서·코드를 읽는다.** 같은 작업의 후속 수정은 그 작업 상태를 이어간다. 설명을 위한 조회마다 브랜치를 만들지는 않는다. 오래된 작업 사본은 파일이 없는 게 아니라 내용이 달라서 알아채기 어렵다. 2026-08-01 낡은 사본을 보고 "자료 테이블이 없다"고 판단해 이미 있는 기능의 설계를 새로 쓴 사고가 있었다.
- 'UI는 main 직행'은 위 로컬 검증·승인 뒤 main에 배포한다는 뜻이다. 브랜치만 푸시하면 GitHub Pages에는 보이지 않는다. 이미 배포한 변경을 되돌릴 때는 `git revert` 후 푸시한다(전파 약 1~2분). 결제·신청·DB·로그인·큰 구조 변경은 브랜치에서 검증하고 작업의 승인 범위에 따라 운영에 반영한다.
- "이 기능이 아직 없다"고 판단하기 전에 `supabase/migrations/` 와 `supabase/functions/` 를 main 기준으로 확인한다.
- 같은 날 다른 작업이 같은 영역을 건드렸을 수 있다 — 같은 타임스탬프의 마이그레이션, 같은 RPC 재생성을 확인한다.

## 실행 환경과 비공개 메모

- Windows·macOS 모두 현재 세션의 OS·셸·`node`·Python·`deno` 경로와 설치 여부를 확인한다. 다른 PC의 버전·절대 경로를 그대로 적용하지 않는다. PowerShell에는 PowerShell 문법을, zsh·bash에는 해당 셸 문법을 사용한다. 없는 lint/build 명령이나 실행기를 가정하지 않는다.
- 프리뷰는 레포 루트에서 설치된 명령을 골라 실행한다: `python -m http.server 5500`, `python3 -m http.server 5500`, Windows Python Launcher가 있으면 `py -3 -m http.server 5500`. 구 macOS의 `wkon-mirror` rsync 미러·nvm 로더는 폐기됐으며 레포를 직접 서빙한다.
- **GitHub Actions 워크플로 수정은 GitHub 웹 편집기를 사용한다.** 기존 git 토큰의 `workflow` 권한 제한에 맞춘 운영 절차다. 뉴스 수집은 `docs/notes/news.md`, 연구실 미리보기 생성은 `docs/notes/lab.md`를 따른다.
- **비공개 메모**: Windows PC의 `C:\Users\cheess\.codex\wkon-notes\INDEX.md`에 상품 방향·자료 확보·쇼츠 제작 규칙이 있다. 해당 영역 작업 전에 읽고 내용을 공개 레포로 옮기지 않는다. 다른 PC에서 이 경로에 접근할 수 없으면 읽었다고 가정하지 않는다. 작업에 꼭 필요한 경우 현재 비공개 메모 위치를 오너에게 확인한다.

## 검증

- **누를 수 있는 것은 눌러 본 뒤의 화면까지 잰다.** 버튼 문구 교체·시트 열림·에러 표시처럼 상태가 바뀐 화면이 검증 없이 나가면 그대로 라이브 사고가 된다(2026-08-01 인앱 배너, 하루 세 번 수정).
  - 글과 버튼을 한 줄 flex 에 나란히 두지 않는다. 버튼 문구를 상태에 따라 바꾸지 않는다 — 피드백은 토스트나 별도 요소로.
- **순서·배치·단 수가 걸린 수정은 1280·768·375px 세 폭에서 잰다.** 데이터 순번을 카드에 대조해 읽는 순서(왼쪽→오른쪽, 위→아래)가 기대와 같은지 좌표로 확인한다. 오너에게 보이는 전·후 화면도 문제가 난 폭으로 찍는다(2026-09-29 후기 목록).
- **속성값이 아니라 계산된 스타일로 확인한다.** `hidden` 속성이 있어도 클래스의 `display` 가 이겨 화면에 보일 수 있다(2026-08-06). `display:flex` 요소에서 특히 그렇다.

### 375px 스크린샷 — Windows·macOS 공통

- 현재 환경에서 사용 가능한 브라우저 도구로 뷰포트를 375px로 맞춘다. 실제 `innerWidth`와 요소 좌표가 375px 기준인지 확인한 뒤 화면을 찍는다. 특정 브라우저 설치 경로나 과거 도구가 있다고 가정하지 않는다.
- 순서·배치 변경은 같은 방식으로 1280·768·375px를 확인한다. Windows CLI에서 폭이 맞지 않으면 아래 iframe 방법을 사용한다.

### Windows Chrome CLI의 대체 방법

- 크롬 경로: `C:\Program Files (x86)\Google\Chrome\Application\chrome.exe`.
- 기존 Windows CLI 환경에서는 **헤드리스 `--window-size=375`만으로 데스크톱 레이아웃이 나왔다**(`--headless=new`도 같음). 약 500px로 그린 화면의 왼쪽 375px만 찍히기도 했다. 어떤 도구를 쓰든 실제 `innerWidth`와 요소 좌표로 뷰포트 폭을 확인한다.
- 방법: `<iframe src="..." style="width:375px">` 래퍼 페이지를 만들어 찍는다.
  1. `--user-data-dir=<임시 폴더>` 를 준다(안 주면 기존 프로필에 붙어 스크린샷이 안 나온다).
  2. 래퍼도 같은 로컬 서버에서 서빙한다(`file://` 로 열면 http iframe 이 빈 화면).
  3. `--virtual-time-budget=8000` 으로 로드를 기다린다.
  4. 첫 실행이 조용히 실패할 때가 있다 — 산출 파일 크기를 확인하고 없으면 한 번 재시도.
- 여러 상태를 한 장에: 검증용 사본에 `?act=` 같은 훅을 넣어 로드 뒤 자동으로 누르게 하고, 375px iframe 을 나란히 놓은 보드 페이지를 찍는다.

### 회원 화면 검증

- 검증용 사본(`__*-test.html`)은 Supabase CDN·`supabase-config.js`를 싣지 않고 가짜 세션·데이터의 `MONC`로 통째로 대체한다. 검증 뒤 사본은 지운다. **config를 먼저 싣고 나중에 덮으면 계측 비콘이 로컬에서도 운영 DB로 나간다.** 결제·인증을 포함해 운영 호출이 발생하지 않는지 확인한다.

### 시간 기반 애니메이션 검증

탭이 화면에 보이지 않는 상태(`document.visibilityState === 'hidden'`)에서는 `requestAnimationFrame` 콜백이 실행되지 않는다. 페이지가 무거워서가 아니다. 이때는 프레임을 직접 돌린다.

1. `fetch` 로 HTML 을 받는다.
2. `src` 없는 빈 `<iframe>` 을 원하는 크기로 붙인다.
3. `contentWindow.requestAnimationFrame` 을 큐에 넣는 함수로 바꾼다.
4. `document.open(); write(html); close()` 로 넣는다(`src` 로 이동하면 바꿔 둔 함수가 사라진다).
5. 큐에서 꺼내 원하는 타임스탬프로 직접 호출하며 프레임마다 상태를 기록한다.

주의: `document.open()` 은 window 의 이벤트 리스너를 지운다 · 콜백은 하나씩 try/catch 로 감싼다 · 이미지 로드 대기가 있으므로 write 와 실행을 다른 호출로 나눈다 · transition 이 걸린 요소는 `getComputedStyle` 대신 인라인 `style.opacity` 를 읽는다.

## UI 원칙 — 안내문 대신 동작

화면에 상시 떠 있는 설명 문단은 읽히지 않는다(2026-08-08 오너 지시). 막아야 하는 동작은 ① 버튼을 살려 두고 누르는 순간 대신 처리하거나 ② 답하기 전에는 다음 화면이 나오지 않는 선택 강제 구조로 만든다. 누른 순간의 한 줄 알림은 읽힌다.

## 오너에게 안내할 때

- **오너가 직접 해야 할 작업은 실행 순서대로 따로 정리한다**(2026-10-05). 각 단계에 누를 메뉴·복사할 내용·완료 기준을 붙이고, 에이전트가 이어서 확인할 일은 마지막에 구분한다. SQL은 대화창 복사 블록, 긴 함수 코드는 바로 열 수 있는 파일 링크로 제공한다.
- **SQL 은 파일 경로가 아니라 대화창에 ```sql 코드로 본문을 붙인다.** 실행 가능한 본문만, 긴 설명 주석은 덜어낸다.
- 확인 쿼리를 여러 번 나눠 시키지 않는다. 꼭 필요하면 `union all` 로 한 번에. 밖에서 확인할 수 있는 것은 프로브로 직접 확인하고 결과만 보고한다.
- **Edge Function은 Supabase 대시보드 > Edge Functions > 함수 선택 > 코드 전체 교체 > Deploy.** 콘솔 배포가 이 프로젝트의 운영 절차다. 안내할 때 콘솔 경로, 붙여넣을 파일, Verify JWT 등 기존 설정 유지 여부를 같이 준다. DB·함수 변경 규칙은 `docs/notes/supabase.md`.
- 배포 여부는 anon key 프로브 응답으로 판별한다.

## 셸 함정

- **PowerShell 5.1 에서 큰따옴표가 든 커밋 메시지는 here-string 으로도 쪼개진다.** 메시지를 UTF-8 파일로 쓰고 `git commit -F <파일>` 로 커밋한다.
- **bash·zsh의 큰따옴표 문자열 안 백틱은 명령 치환으로 해석돼, 백틱으로 감싼 토큰이 사라진 채 파일이 써진다.** 스크립트는 성공으로 끝나서 알아채기 어렵다. 백틱이 든 본문은 파일 편집 도구로 쓰거나 heredoc(`<<'EOF'`)으로 넘기고, 쓴 뒤 `rg`로 확인한다.

## 이미지·영상 생성

- **오너는 크레딧 소모 없이 만들기를 원한다.** 생성 도구를 부르기 전에 경로를 묻는다. 기본은 프롬프트를 주고 오너가 웹에서 직접 뽑아 파일을 넘기는 방식이다.
- 프롬프트를 줄 때는 자산마다 어느 도구로 뽑는지 적는다(정지 이미지와 영상 클립은 도구·비용이 다르다).
- 한 세트 안에서 모델을 섞으면 톤이 어긋난다 — 기존 이미지를 참조로 넣거나 한 모델로 통일한다.
